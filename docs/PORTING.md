# Porting rules: Aml.Engine (C#) to AmlEngine.js (TypeScript)

AmlEngine.js is a faithful port of Aml.Engine 4.5.2. The decompiled C# source is the
specification; the original engine, run by `oracle/`, is the judge. Where the two disagree,
the oracle wins. Every rule below exists so that ported code behaves like the original and so
that different files ported at different times fit together.

## Layout

| C# namespace | TS folder |
|---|---|
| `System.Xml.Linq` | `src/xml/` (done, byte-exact with .NET) |
| `System.*` value types and helpers (DateTime, TimeSpan, decimal, Guid, XmlConvert, exceptions, events) | `src/system/` |
| `Aml.Engine.XML` | `src/engine/xml/` |
| `Aml.Engine.Xml.Extensions` | `src/engine/xmlext/` |
| `Aml.Engine.Schema` | `src/engine/schema/` |
| `Aml.Engine.CAEX` | `src/engine/caex/` |
| `Aml.Engine.CAEX.Extensions` | `src/engine/caex/extensions/` |
| `Aml.Engine.CAEX.Commands` | `src/engine/caex/commands/` |
| `Aml.Engine.AmlObjects` | `src/engine/amlobjects/` |
| `Aml.Engine.Services` (+ Interfaces, Model) | `src/engine/services/` |
| `Aml.Engine.Adapter`, `Streaming`, `Resources` | `src/engine/<name>/` |

One TS file per C# file, same base name. Keep member order of the C# file so a diff
side by side stays readable. Doc comments (`/// <summary>`) become TSDoc, shortened
where they only repeat the name.

## Names

- Classes, interfaces, enums, enum members: unchanged (`InternalElementType`, `CAEXSchema.CAEX3_0`).
- Methods and properties: lower camel case by one rule, applied mechanically: lower-case the
  leading run of capitals, except its last capital when a lower-case letter follows.
  `CAEXFile` -> `caexFile`, `ID` -> `id`, `IDService` -> `idService`, `RefBaseClassPath` ->
  `refBaseClassPath`, `AMLFile` -> `amlFile`, `New_CAEXDocument` -> `new_CAEXDocument`,
  `CAEXPath()` -> `caexPath()`, `XName()` -> `xName()`. Underscores stay.
- Constants (`const`, `static readonly` fields): unchanged when they are public API
  (`CAEXObject.GUID_FORMAT`), otherwise camel case.
- Private fields: `_name` as in C#.

## Types

| C# | TS |
|---|---|
| `string` | `string` (null stays `null`; never turn null into `''`) |
| `bool` | `boolean` |
| `int`, `short`, `sbyte`, `byte`, `ushort`, `uint`, `float`, `double` | `number` |
| `long`, `ulong` | `bigint` |
| `decimal` | `Decimal` from `src/system` |
| `DateTime`, `TimeSpan`, `Guid`, `Uri` | classes from `src/system` |
| `object` | `unknown` |
| `XElement` etc. | `src/xml` classes |
| `IEnumerable<T>` | `Iterable<T>`; lazy `yield` methods become generator functions |
| `List<T>` / arrays | `T[]` |
| `Dictionary<K,V>` | `Map<K,V>` |
| `Type` parameters (`typeof(T)`) | the class constructor (`typeof InternalElementType`) |

Null handling: C# `a?.b` maps to `a?.b ?? null` where the result is observable
(JS would give `undefined`). Public API returns `null`, never `undefined`.

## Equality: the one rule that silently breaks things

`CAEXWrapper` overloads `==` and `!=` (equal when both wrap the same `XElement`).
In the decompiled source this looks like plain `==`. Every `==` / `!=` whose operands are
statically `CAEXWrapper` or a subclass must become `CAEXWrapper.equals(a, b)` /
`!CAEXWrapper.equals(a, b)`. `(object)a == b` in C# is reference equality: `a === b`.
`string ==` is value equality (`===`). `XName`/`XNamespace` are interned: `===` is correct.
`object != object` on boxed strings (`SetAttributeValueCmd.Execute`) is reference inequality
in C#; see `docs/deviations.md`.

## Where every type lives

`docs/type-map.tsv` (generated by `scripts/gen-registry.py`) fixes, for every C# type, the TS
module and the export name. Nested types are exported as `Outer_Inner` from the outer type's
module and additionally attached as a static property (`CAEXDocument.CAEXSchema`). A generic
type that has a non-generic twin in C# gets the suffix `_1` (`CAEXWrapper_1` for
`CAEXWrapper<TDataType>`, `NamedElementSequence_1`). `docs/extension-methods.tsv` lists every
extension method with its `this` type and declaring static class; use it to resolve calls such
as `node.CAEXSchema()` (overloads differ by `this` type).

## Overloads, out/ref, optional parameters, indexers

- Overloads become one method that dispatches on the runtime type and number of its arguments,
  in the order the C# compiler would pick. Callers in other files call it with the C# argument
  list, so every overload must be supported by the single method.
- `out`/`ref` parameters: the method returns an object with `result` (the C# return value, if
  not void) plus one field per out/ref parameter, named after it in camel case:
  `xmlSchemaInfo(p, c)` returns `{ result: boolean, info: XmlSchemaElementInfo | null }`,
  `validate()` returns `{ result: boolean, violationLog: string[] }`. Always this shape, also
  for `TryX` methods, so calls across files stay mechanical.
- Optional parameters keep their C# default values.
- Indexers (`this[int]`, `this[string]`) become a method `item(...)`; a setter becomes
  `setItem(..., value)`.
- Generic methods whose type parameter matters at run time (`Container<T>()`,
  `FindByPath(..., Type)`) take the class constructor as an extra (last) parameter.
- Properties stay properties (getters/setters); `ToString()` becomes `toString()`,
  `GetEnumerator()` becomes `[Symbol.iterator]()`, `Equals`/`GetHashCode` become
  `equals(other)` and `equalityKey()` (see src/system/linq.ts).

## Static classes

A C# static class becomes `export class X { private constructor() {} static ... }` with static
methods and static getters for static properties. Extension methods are static methods whose
first parameter is the `this` argument. Static classes may be imported directly (they are never
extended), but their own run time use of other classes goes through the registry as well.
Static fields whose initializer needs another module are initialized lazily (static getter).

## C# idioms

- `(bool)element`, `(string)element`, `(DateTime)element` etc. (explicit XElement/XAttribute
  conversions) as XLinq defines them: `(bool)e` is `XmlConvert.toBoolean(e.value.toLowerCase())`,
  `(string)e` is `e?.value ?? null`, `(DateTime)e` is `XmlConvert.toDateTime(e.value,
  XmlDateTimeSerializationMode.RoundtripKind)`, `(int)e` is `XmlConvert.toInt32(e.value)`.
- `x as T` for classes: `x instanceof T.Name ? x : null`; `(T)x` casts are type assertions.
- `string.IsNullOrEmpty(s)`: `isNullOrEmpty(s)` from src/system/strings.ts (not `!s`).
- String comparisons in C# `switch` and `==` are ordinal: `===`.
- `lock`, `ConfigureAwait`, `Dispose` patterns: drop, keep behaviour.
- LINQ: `from(seq)` from `src/system/linq.ts` gives an `Enumerable` with the C# operators
  (`where`, `select`, `firstOrDefault`, `except`, `toList`, ...), lazy like C#.

## System layer

`src/system` provides the .NET types: `DateTime`, `DateTimeKind`, `TimeSpan`, `Decimal`, `Guid`,
`Uri`/`UriKind`, `XmlConvert`, `XmlDateTimeSerializationMode`, `XmlTypeCode`, `Convert`
(base64), `EventSource`, the exceptions, parse helpers (`Parse.tryParseInt32(s)` etc. returning
the value or null), `linq`. Method names follow the naming rule (`DateTime.now`,
`XmlConvert.toString(value)`, `XmlConvert.toDateTime(s, mode)`, `decimal.toString()`).

## Interfaces

C# interfaces become TS interfaces for typing. Because TS interfaces do not exist at run
time, `x is IFoo` checks use `implementsInterface(x, 'IFoo')` from `src/engine/interfaces.ts`.
Every class that implements interfaces in C# registers them right after its declaration:
`registerInterfaces(InternalElementType, 'IInternalElementContainer', 'IMirror', ...)`.
Interface registration is inherited. An interface module that extends other interfaces in C#
declares that once at module level: `registerInterfaceBases('ICAEXObject', 'ICAEXBasicObject', ...)`.

## Module cycles

Base classes must not import subclasses at run time (an `extends` over a module cycle fails at
load). Run time references to other wrapper classes go through the registry:
`import { T } from '../registry.js'` and `x instanceof T.InternalElementType`,
`new T.RoleRequirementsType(node)`. Each class module registers itself at its end:
`T.InternalElementType = InternalElementType`. Use `import type` for type positions.
`src/engine/index.ts` imports every module so the registry is complete.

## Extension methods

C# extension methods become exported functions in the module of their static class
(`CAEXBasicObjectExtensions.findCaexObjectFromId(obj, id)`), exported as a namespace object
named like the C# class. Engine code calls them as functions. Selected extensions are also
exposed as instance methods for convenience in `src/engine/fluent.ts`; that file is the only
place where prototypes are extended.

## LINQ and iteration

Port LINQ to plain loops or array methods, but keep evaluation semantics: `.ToList()` and
`.ToArray()` snapshot, everything else is lazy. Where C# iterates a live XLinq sequence
(`Elements()`, `Attributes()`, `Nodes()`) while modifying the tree, the XLinq port behaves
like .NET (live, pointer based), so a literal port stays correct. `First()` throws
`InvalidOperationException` when empty, `FirstOrDefault()` returns `null`.

## Exceptions

Throw the classes from `src/system/exceptions.ts`, named like their .NET counterparts
(`ArgumentNullException`, `ArgumentException`, `InvalidOperationException`,
`NotSupportedException`, `XmlException`, ...). Keep messages and parameter names.
Swallowing `catch` blocks stay swallowing.

## Events

`event EventHandler<T>` becomes an `EventSource<T>` from `src/system/events.ts` with
`subscribe`/`unsubscribe`, raised synchronously in subscription order. `INotifyPropertyChanged`
maps to the same mechanism (`propertyChanged`).

## Static state

C# static members stay static (`ServiceLocator`, `CaexCommand.isSilent`, `DocumentTable`).
The engine is single threaded in JS; `lock` blocks disappear.

## Aml.Engine.Services and Aml.Engine.Resources

Aml.Engine.Services 4.3.1 (a separate NuGet package on top of Aml.Engine) and the types of
Aml.Engine.Resources 4.2.1 (a dependency of Aml.Engine) are ported by the same rules. The type map
lists them with their assembly in the last column (`scripts/gen-registry.py <aml-engine-dir>
--resources <dir> --services <dir>`).

| Assembly, namespace | TS folder |
|---|---|
| Aml.Engine.Resources (`.Catalogue`, `.Files`, `.AMLStandard`) | `src/engine/resources/` (`catalogue/`, `files/`, `libraries/`) |
| Aml.Engine.Services: `Aml.Engine.Services` | `src/services/` |
| `.Lookup`, `.UndoRedo`, `.Generique`, `.TransformatorService`, `.AMLTransformer` | `src/services/lookup/`, `undoredo/`, `generique/`, `transformator/`, `amltransformer/` |

- Resources types belong to the engine (registry `T`, exported by `amlengine-js`). Services types
  are not in the registry: they import each other directly (no base class imports a subclass) and
  use `T` for engine classes. They are exported by `amlengine-js/services`, which shares the engine
  modules with `amlengine-js` (tsup.config.ts), so a service registered there is the one the
  engine's `ServiceLocator` finds.
- `Task<T>` becomes `Promise<T>`; a C# tuple result `(Document, Message)` becomes
  `{ document, message }` as in the interfaces of `src/engine/services/interfaces/`. An `async`
  method stays `async`; the synchronous twin that calls `.Result` on it runs the same code
  without awaiting where the C# code completes synchronously (local files) and fails where it
  would need the network (below).
- Network access follows the engine (`src/engine/streaming/DocumentStreaming.ts`): asynchronous
  methods use `fetch`; synchronous methods read local files in Node (`getFs()` of
  `src/engine/amlobjects/internal/NetPath.ts`). Where C# would block on an http(s) request in a
  synchronous method, the port takes the path C# takes when that request throws, with the message
  of a `NotSupportedException` saying that synchronous network access is not possible. FTP
  (`FtpWebRequest`) is not supported and takes the same failure path. Document each such place in
  docs/deviations.md.
- `HttpClient` becomes `fetch`, `HttpResponseMessage` becomes `Response`. Octokit calls become the
  REST requests Octokit sends: `GetRawContentByRef(owner, repo, path, ref)` is `GET
  https://api.github.com/repos/{owner}/{repo}/contents/{path}?ref={ref}` with `Accept:
  application/vnd.github.v3.raw`, `GetAllContentsByRef` the same with `Accept:
  application/vnd.github.v3+json` (a file gives one object, a folder an array); credentials are
  sent as `Authorization: token <token>`; a 404 is Octokit's `NotFoundException`.
- `SemaphoreSlim(1, 1)` becomes `AsyncLock` (`src/system/AsyncLock.ts`): FIFO, `currentCount`,
  `waitAsync()`, `release()`. JS interleaves at every `await`, so the lock is needed exactly where
  C# has one.
- `ConcurrentDictionary`, `ConcurrentBag`, `lock`: plain `Map`, arrays and code; keep the order
  of enumeration C# gives (ConcurrentBag enumerates the most recently added first).
- PLINQ (`AsParallel()`) becomes sequential LINQ; where the C# result order is unspecified, take
  the order of the sequential query and note it in the port notes.
- `INotifyPropertyChanged.PropertyChanged` becomes an `EventSource<PropertyChangedEventArgs>`
  property `propertyChanged`.
- `DateTime.Now.ToLongTimeString()` and other culture formats use the invariant culture, as the
  oracle does.
- System.Text.Json (de)serialization uses `src/system/Json.ts` (the emulation of the options and
  escaping of System.Text.Json the engine already needs).
- Port notes per package in `docs/port-notes/services-<package>.md` (and `resources.md`).

## Tests

Every ported behaviour is checked against the oracle, never against expectations written by
hand from reading the C# code:

- read model: `oracle dump` (paths, references, inheritance, mirrors) compared by
  `test/engine/dump.oracle.test.ts`;
- write operations: scripted operation sequences run by `oracle ops` and by the JS runner,
  compared on the saved XML and on the recorded results;
- anything the oracle cannot express is a gap and is listed in `docs/coverage.md`.
